# Kimi, Hermes, Grok Build and DCode native agent registration

Recorded 2026-10-22; planning only against plugnz `2795dee`. No native installation, model call, provider charge, or repository modification. First-party upstream sources were read at the immutable pins below; existing host qualification was read from the local checkout. Source support is not installed-version qualification.

## Recommendation

Advance **Grok Build** to a bounded native qualification spike. Keep **Kimi, Hermes and DCode** decisions open: their currently evidenced plugin route does not yet establish portable named-agent registration with per-agent model selection. Do not make a prompt command or a generic delegation API stand in for a registered native agent.

The existing contract remains explicit destination model > user alias mapping > package alias mapping > omit. No `inherit` sentinel, runtime wrapper, portable tools/permissions, or provider guessing. Native behavior after omission must be measured per host.

## Grok Build: native plugin agent directory is documented; model projection still requires parser proof

- **Proposed route:** generated native Markdown under the existing managed plugin's `agents/` directory, then the current marketplace install/activation lifecycle. First-party plugin documentation explicitly discovers this directory, and subagent documentation describes plugin identities such as `my-plugin:reviewer` in `spawn_subagent`'s `subagent_type` enum. No separate user-agent directory should be introduced.
- **Models/tools:** upstream documents per-type native `[subagents.models]` overrides and parent-model inheritance when no override exists; these are native runtime behavior, not permission to write global model config. The exact plugin Markdown model parser, accepted identifiers, definition-vs-native-override precedence, and unavailable explicit-model failure remain to be traced before choosing emitted syntax. Native child tools depend on its agent definition; parent MCP is inherited by default. Leave portable tools and permission fields absent.
- **Lifecycle implication:** retain plugnz's existing owned activation symlink and shadow-collision protections, immutable generated source, rollback and removal. Native reload/new-session discovery and removal of the generated agent must be checked. Existing loader evidence covers skills/commands/MCP rather than agents; it cannot be reused as agent execution proof.
- **Next bounded proof:** inspect the pinned agent loader/frontmatter parser, then qualify one plugin with two agents in an isolated existing Grok installation: one explicit native model identifier, one omitted model. Read native discovery and resolved child configuration; separately obtain authorized native child execution. Exercise alias-only update, rename/removal and failed-update rollback. If a native loader test cannot establish field parsing, leave model registration unverified.
- **Pins:** [plugin discovery/lifecycle](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/09-plugins.md), [subagent types/models/MCP defaults](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/16-subagents.md), [definition resolution](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-subagent-resolution/src/definition.rs). Existing plugnz evidence: `docs/hosts/grok.md` (source `a549186...`, exercised binary 1.0.41, different revisions explicitly disclosed).

## Kimi: identify the actual host before selecting a registration route

- **Decision open:** plugnz's qualified target is Kimi Code **2.0.1** with `KIMI_CODE_HOME`, `kimi.plugin.json` and loopback plugin APIs. Its existing manifest projection admits name/version/description/skills/commands/MCP, not agents. The inspected public Moonshot `kimi-cli` tree offers native subagent types but has not been bound to that installed Kimi Code loader. It is insufficient evidence for extending this adapter.
- **Models/tools:** public `kimi-cli` has `AgentTypeDefinition.agent_file`, optional `default_model`, default `ToolPolicy(mode="inherit")`; its builder resolves launch override > effective model > type default and calls `clone_llm_with_model_alias`. This is a promising source lead only; accepted plugin registration format, model key semantics, omission behavior and tool defaults for the actual 2.0.1 host remain unknown.
- **Lifecycle implication:** retain existing native install/enable/remove API and guarded registry readback. Do not hand-write a new registry or copy upstream CLI agent files into unrelated user directories. Any projected native agent declaration must remain inside owned plugin lifecycle and cannot be bypassed by native refresh.
- **Next bounded proof:** bind an already-installed actual binary to its bundled loader/source and inspect its plugin schema for an agent declaration plus dispatch path. If present, record exact schema and native model resolution; if absent, leave unsupported/unverified and stop. No installation, runtime abstraction or package upgrade is required for this reconnaissance.
- **Pins:** [public CLI type definitions](https://github.com/MoonshotAI/kimi-cli/blob/9ab1286b8fe4e6bcd116949a27ce5e0ac3389c82/src/kimi_cli/subagents/models.py), [builder/model resolution](https://github.com/MoonshotAI/kimi-cli/blob/9ab1286b8fe4e6bcd116949a27ce5e0ac3389c82/src/kimi_cli/subagents/builder.py). Actual host evidence: `docs/hosts/kimi.md`, `docs/evidence/kimi-native-loader-20260922.json`, `docs/evidence/kimi-public-lifecycle-20260922.json`.

## Hermes: delegation exists; reusable native agent registration is unproven

- **Decision open:** the inspected native delegation API spawns children from a goal/context. No reusable named agent definition/registration surface was established by this bounded scan. Plugin skill loading, slash-command registration and injection are already evidenced but do not establish agent support.
- **Models/tools:** at the inspected latest source, delegate children inherit parent model unless native `delegation.provider` / `delegation.model` configuration pins routing; child toolsets derive from the parent with native restrictions. These are global delegation settings, not a demonstrated per-agent model field. Writing a Python companion that constructs children or changes global routing would exceed this packaging-only contract.
- **Lifecycle implication:** existing managed package/companion transaction, exact source-version admission and guarded removal remain applicable only if a real registration API is found. Current exact admitted source revisions end at `7dbbb0f4a6ebeec9a8714ec37fa41340fe9e4e00`; inspected newer source is not admitted by association. Never run Hermes merely to identify its version: the existing host evidence documents bootstrap recovery side effects.
- **Next bounded proof:** inspect the plugin context API and all native definition-loading entrypoints at an already-supported revision for named agent registration with optional model. If none exists, record unsupported for that revision and keep decision open for later upstream work. A generic `delegate_task` call alone fails acceptance.
- **Pin:** [native delegation implementation and schema](https://github.com/NousResearch/hermes-agent/blob/8237c7f8ec179c88857f24a174509d985af704b7/tools/delegate_tool.py), especially child construction and `_DESCRIPTION_TAIL`. Existing evidence: `docs/hosts/hermes.md` and `docs/evidence/hermes-native-loader-7dbbb0f-20261015.json`.

## DCode: user subagent parser exists; plugin agents explicitly unsupported

- **Decision open / present plugin route unsupported:** current first-party plugin manifest source explicitly lists `agents` and `commands` as unsupported component directories. A separate native parser supports `.deepagents/agents/<name>/AGENTS.md`; that is not evidence that plugins register these definitions. Do not quietly convert plugin content into standalone global files or invent a Python extension registration API.
- **Models/tools:** the user-subagent parser accepts optional `model` in `provider:model-name` form and returns `None` when omitted; it reads name/description/body and no tools field. Downstream runtime treatment of model `None` and native tools must still be traced. Parser acceptance alone does not establish execution or unavailable-model failure.
- **Lifecycle implication:** existing Managed profile for released **0.1.83** keeps agents as a typed gap. If upstream exposes a native plugin registration extension, its ownership, collision handling, unload and rollback must be qualified before admission; current skill/MCP/hook/resource lifecycle proofs do not cover this.
- **Next bounded proof:** trace current native user-agent loader callers and public ExtensionAPI for a first-party plugin registration seam. If no seam exists, preserve unsupported rather than add a runtime wrapper. A separate registration route would require an explicit evidence-backed design decision and complete owned lifecycle, including removal; it cannot be inferred from the parser alone.
- **Pins:** [plugin manifest: unsupported agent directory](https://github.com/langchain-ai/deepagents/blob/b4ac8829692785a221150658401ae558f4bff3f3/libs/code/deepagents_code/plugins/manifest.py), [native user subagent parser](https://github.com/langchain-ai/deepagents/blob/b4ac8829692785a221150658401ae558f4bff3f3/libs/code/deepagents_code/subagents.py). Existing evidence: `docs/hosts/dcode.md`, `docs/evidence/dcode-native-batch2-20260923.md`, `docs/evidence/dcode-native-update-0.1.83-20261009.json`.

## Acceptance and limits

Closing [Choose native agent registration for Kimi, Hermes, Grok Build and DCode](https://github.com/archeism/plugnz/issues/93) should require a route decision per host backed by a parser/registration source pin and a bounded proof plan. This reconnaissance supplies one plausible route and three explicit unresolved decisions, not four qualified adapters. Implementation qualification additionally needs actual native discovery/child execution, model precedence/omission/error behavior, default tools, collision/refusal and full install/update/remove/rollback evidence. Skill instructions unchanged; no observed failure warranted a skill revision. Parent owns review, checkpoint and any GitHub updates.
