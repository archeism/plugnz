# Pi and OpenCode native agent routes

Date: 2026-10-22. Local base: `plugnz@2795dee`. Research only: no implementation, native installation, model invocation, or GitHub writes. Acceptance: identify an existing execution owner and model/tool semantics; distinguish source evidence from native qualification. Decision remains open where unproven. Skill decision: research/machine-local/RSI/factory skills unchanged; this bounded source review supplies no tested reason to revise them. Downloaded source evidence is retained outside Git at `/root/.local/state/plugnz-agent-parity-plan-20261022/source/`.

## Recommendation

**OpenCode:** advance an agent-registration plugin candidate to a version-pinned probe. A generated plugin can use the native configuration hook to populate `config.agent` with namespaced agents; OpenCode's own task tool executes them. This fits a native plugin packaging route more closely than separately writing agent Markdown. Native Markdown/config files also exist and provide a useful control probe, but they are not automatically an approved plugnz distribution route.

**Pi:** keep route selection open. There is a first-party example extension and a separately maintained community package that already delegate to Pi. Reusing one can avoid a plugnz-authored execution runtime. The inspected package contract does not itself expose agent definitions as a package resource. Decide whether an explicitly pinned existing extension plus owned definitions qualifies for the intended native route before implementation; do not report absence of a proven route as impossibility.

Both require an explicit scope amendment from the current hook-only Pi/OpenCode allowance. `SPEC.md` §§Portable context hooks and migration scope, and `AGENTS.md`, admit hook packages only; portable-agents.md currently qualifies Claude, Codex and ZCode. Research authorization does not itself approve shipping a new agent route. This does not reopen excluded standalone skill/command delivery.

## OpenCode evidence and boundary

Frozen release source: `anomalyco/opencode@148842ef7cb1bc34192b3fff57d0f9721ab9c801` (`v1.19.4`). API release `target_commitish` differs from the resolved tag commit; all release links below use the resolved tag commit. This is a research candidate, not a qualified plugnz version.

- Plugin API declares `config?: (input: Config) => Promise<void>`; loader invokes that callback with the loaded configuration. Source supports registering definitions through configuration without a custom delegation tool. [Plugin API](https://github.com/anomalyco/opencode/blob/148842ef7cb1bc34192b3fff57d0f9721ab9c801/packages/plugin/src/index.ts#L225), [loader](https://github.com/anomalyco/opencode/blob/148842ef7cb1bc34192b3fff57d0f9721ab9c801/packages/opencode/src/plugin/index.ts#L244).
- Native agent construction consumes `cfg.agent`, including prompt, description, model and mode; a new role receives host defaults and user permissions. Emit description, prompt, `mode: subagent`, and model only when resolved. Omit tools and permissions, preserving native policy. [Agent construction](https://github.com/anomalyco/opencode/blob/148842ef7cb1bc34192b3fff57d0f9721ab9c801/packages/opencode/src/agent/agent.ts#L267).
- Native task execution selects the agent's model, otherwise the invoking assistant's provider/model. Native child permissions have host-specific restrictions; preserving native tools means retaining those semantics, not promising unrestricted or identical parent tools. [Task model](https://github.com/anomalyco/opencode/blob/148842ef7cb1bc34192b3fff57d0f9721ab9c801/packages/opencode/src/tool/task.ts#L181), [child permissions](https://github.com/anomalyco/opencode/blob/148842ef7cb1bc34192b3fff57d0f9721ab9c801/packages/opencode/src/tool/task.ts#L140).
- Official documentation supports JSON agents and Markdown at `~/.config/opencode/agents/` or `.opencode/agents/`, with the filename becoming the agent name. Native subagents can be invoked by the host or by @ mention. [Agent docs](https://opencode.ai/docs/agents/).

Unknowns requiring the probe: callback mutation ordering versus agent-cache initialization; collision refusal across user config and other plugins; namespace survival; unloading after removal/reload; preservation of instruction bytes; actual explicit-model and omission behavior; owned lifecycle/rollback integration. API presence alone does not qualify runtime behavior.

Version caveat: current dev is `e965774fa0e2a8ffb27bf02827a2c3c6a8c0f45b`, which has moved relevant files and exposes an agent transform domain. Do not mix that API with release v1.19.4's hook. [Dev agent API](https://github.com/anomalyco/opencode/blob/e965774fa0e2a8ffb27bf02827a2c3c6a8c0f45b/packages/plugin/src/promise/agent.ts). Old source paths returned 404 on dev; preserved as a research navigation miss, not evidence the feature is absent.

## Pi evidence and boundary

Frozen first-party source: `earendil-works/pi@74f46864025c68504cd10c89eeb626b7e3d64cea` (the former badlogic/pi-mono URL redirects here). No corresponding installed/released version was qualified.

- Pi packages distribute extensions, skills, prompt templates and themes. The documented manifest/resource list does not include agents. A package can load an extension, but that fact alone does not establish definition discovery. [Package contract](https://github.com/earendil-works/pi/blob/74f46864025c68504cd10c89eeb626b7e3d64cea/packages/coding-agent/docs/packages.md).
- The first-party subagent example is an extension, not a built-in package agent registry. Its discovery reads Markdown under the user agent directory and nearest project `.pi/agents`; names and descriptions are required. Project and user scopes exist; project agents take precedence when both are selected. [Discovery implementation](https://github.com/earendil-works/pi/blob/74f46864025c68504cd10c89eeb626b7e3d64cea/packages/coding-agent/examples/extensions/subagent/agents.ts#L128).
- That extension registers a `subagent` tool and spawns native Pi processes. A resolved model is passed to the child; omitted model uses dispatch defaults from the parent context. `--tools` is passed only when agent tools are specified, so portable projection should omit tools. The extension, rather than plugnz, owns dispatch and child lifetime. [Child invocation](https://github.com/earendil-works/pi/blob/74f46864025c68504cd10c89eeb626b7e3d64cea/packages/coding-agent/examples/extensions/subagent/index.ts#L298), [registration/defaults](https://github.com/earendil-works/pi/blob/74f46864025c68504cd10c89eeb626b7e3d64cea/packages/coding-agent/examples/extensions/subagent/index.ts#L470).
- Community alternative: `nicobailon/pi-subagents@07fe5a70e63ce59bb4ca9f19d353fd20ec3a710a` is independently maintained and documents `pi install npm:pi-subagents`, Pi >=1.2.0, custom agents and delegation. It is **not Pi core**, even though loaded through Pi's native extension system. README evidence establishes a candidate dependency, not a qualified portable-agent contract. [Package maintainer README](https://github.com/nicobailon/pi-subagents/blob/07fe5a70e63ce59bb4ca9f19d353fd20ec3a710a/README.md).

Unknowns: which existing extension is acceptable as an explicit dependency; exact package/release and compatibility range; package-owned definition discovery without unmanaged global copies; namespace/collision behavior; whether its child loader retains the required native tools/extensions; explicit and omitted model handling for the chosen extension; install/update/remove/rollback ownership. The upstream example's behavior must not be attributed to the community extension.

## Smallest next probe and acceptance

First record scope and the intended native dependency route in [Decide native agent routes for Pi and OpenCode without a custom runtime](https://github.com/archeism/plugnz/issues/94); no implementation is authorized by this note alone. For OpenCode, use a disposable home and pinned release to load one minimal generated plugin with one namespaced agent and inspect native discovery. Compare with a native Markdown control. For Pi, first inspect the selected extension's discovery entry point and determine whether package-owned definitions can be registered without writing a new runtime; only then load it in a disposable home.

For both, freeze four mapping fixtures: explicit destination model > user alias mapping > package alias mapping > omitted field. Do not guess cross-harness equivalents or emit `inherit`. Keep tool/permission/effort fields absent. Next native execution qualification must prove actual child identity, selected model (including omitted inheritance), unchanged instructions, native tool availability and host policy, observed invalid-model/fallback behavior under the pending native-policy decision, collision refusal, update/removal/reload and rollback. Start with discovery/config checks that require no paid model call; native execution remains a separate, explicitly authorized qualification step under the parent plan.
